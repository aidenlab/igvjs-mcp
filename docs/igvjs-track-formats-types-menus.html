igv.js Track Formats, Types and Menus

How a loaded file becomes a track, what separates a format from a type, and which gear-menu items each kind of track offers.

Format and type are two different questions

Every track config ends up with two strings, format and type. They are easy to blur together because a file's extension usually decides both, but they control separate halves of the system and can vary independently.

format: how are the bytes read?

Picks the data source, reader and parser. It answers what the file looks like on disk: binary or text, indexed or not, which columns mean what.

  • Consumed by FeatureSource() in js/feature/featureSource.js, by the BAM/CRAM loaders, and by FeatureParser.setDecoder(), which has one decoder per text format.
  • Examples: bed, narrowpeak, gff3, bigwig, tdf, vcf, bam, bedpe.
  • About 45 recognized values.
type: how is it drawn and operated?

Picks the Track subclass, which owns drawing, popups, session state and the gear-menu items. It answers what the data means visually.

  • Consumed by getTrack() in js/trackFactory.js, and by the menu builder in js/ui/menuUtils.js, which keys several decisions on the type string itself.
  • Examples: annotation, wig, alignment, variant, interact, seg.
  • About 20 Track classes, with roughly 35 accepted type strings once aliases are counted.

The relationship is many-to-many in both directions:

  • Many formats, one type. bigwig, wig, bedgraph and tdf all become a wig track. A dozen text formats (bed, gff3, gtf, refgene, narrowpeak, rmsk…) all become an annotation track.
  • One format, several types. A bigbed file becomes annotation or interact depending on its autoSql table name. A .bed file becomes interact or gcnv if its track line says type=interact or type=gcnv. A hic file is drawn as an interact track.
  • Type usually follows from format, which is why most configs only need a url. Setting type explicitly overrides inference, and that is the only way to reach some Track classes (junction, shoebox, merged, image, blat).

How a config is resolved into a track

All of this happens in Browser.createTrack() (js/browser.js, around line 1234). Format is settled first, then type.

  1. Settle the format

    First match wins:

    • config.format, lowercased.
    • fasta if the config has a fastaURL.
    • The file name (config.filename or the URL). .gz/.bgz and then .txt/.tab/.tsv are stripped before the extension is read; bw becomes bigwig, bb becomes bigbed, fa/fna become fasta; *refGene.txt(.gz) is special-cased to refgene. Unknown extensions give nothing.
    • The file contents: the first 1000 bytes are fetched (gunzipped if needed) and tested for magic numbers (BAM, CRAM, bigWig, bigBed, TDF), then header lines (##fileformat=VCF, ##gff-version, any ##fileformat=X), then QTL, GWAS and HiCCUPS column signatures.
    • For sourceType: "htsget", the htsget reader is asked.

    js/util/fileFormatUtils.js · inferFileFormat

  2. Translate legacy type names

    Old-style types that were really formats are split into a type plus a format: bed → annotation + bed, bam → alignment + bam, vcf/vcftabix → variant + vcf, aed → annotation + aed. Also annotations → annotation, alignments → alignment, junctions → junction, t2d → gwas, and the old featureType key becomes type.

    js/util/trackUtils.js · translateDeprecatedTypes

  3. Infer the type from the format, if no type was given

    inferTrackType(format) is a fixed table (next section). Anything it doesn't list falls through to annotation. If neither a type nor a format could be found, the load fails with "Unrecognized track".

    js/util/trackUtils.js · inferTrackType

  4. Open the file for BED-like formats

    For bed, bigbed, biggenepred and bignarrowpeak the table returns a placeholder, bedtype, meaning "read the header before deciding". A feature source is built early and asked for trackType():

    • bigBed / bigWig: wig for bigWig; interact if the autoSql table is interact or chromatinInteract; otherwise annotation.
    • Text BED: the track line's type= (interact, gcnv), which also overrides the format.
    • Anything unknown: annotation. The source is kept on the config so the file isn't opened twice.
  5. Record the type and apply defaults

    The inferred type is written back to config.type, so a saved session carries it. Then browser.trackDefaults[type] fills any unset config properties.

  6. Construct the Track

    getTrack(type) maps aliases onto a constructor: annotation, genes, snp, fusionjuncspan → feature; maf, mut → seg; junctions, splicejunctions → junction; and eqtl and interaction are registered as extra keys for QTLTrack and InteractionTrack. The track's own this.type keeps the original string (for example genes), which matters for menus; see the pitfalls below.

    js/trackFactory.js · getTrack

Gear-menu items by track type

The gear menu is assembled in MenuUtils.trackMenuItemList() (js/ui/menuUtils.js). It wraps the track's own menuItemList() in a frame of common items, in this order:

  1. Set track height (all but sequence)
  2. Set track name (all but sequence)
  3. Set / Unset track color if the type is in the color-picker set (annotation, wig, alignment, variant, interact, shoebox) and the graph isn't a heatmap; plus Set / Unset alt color for wig and annotation
  4. The track's own items (the last column below)
  5. Set visibility window if the type is alignment, annotation, variant, qtl, eqtl, snp, shoebox or wig, or the config sets visibilityWindow
  6. Remove track unless removable: false

When several tracks are selected, the menu applies to all of them. If they share a type you get that type's full menu, and wig tracks also get Group autoscale. Mixed types get only height, color and remove. The ruler and ideogram have no gear menu.

Right-click menus are separate. Several tracks also implement contextMenuItemList(clickState), shown on right-click over data rather than from the gear: annotation (View / Copy feature sequence), alignment (Group / Sort by base, View / Copy / BLAT read and soft-clipped sequence, View mate in split screen), variant (Sort by genotype), seg (Sort by value / count), interact and qtl (circular view, Highlight associated features), and sequence.

Pitfalls in how the two interact

The factory maps aliases to classes, but the menu builder tests the raw track.type string. So two configs that produce the same class can produce different menus. These came out of reading the code for this document and are worth checking against intent.

Annotation aliases lose the color picker. type: "annotation" gets Set track color and Set alt color. type: "feature", "genes" or "snp" build the same FeatureTrack with neither, because only annotation is in colorPickerTrackTypeSet. Inferred types are always annotation, so this only bites hand-written configs and sessions.
Same for interactions. interact gets a color picker, interaction does not.
maf/mut lose Fill. SegTrack offers Fill only when this.type === "seg".
The visibility-window list names types that are aliases. snp and eqtl get the item, but genes, feature and interact do not unless the config sets visibilityWindow.
bedtype in the color-picker set is dead. It is a placeholder that createTrack always resolves before a track exists, so no track ever has it.
Some formats parse fine but never reach their dedicated track by inference. shoebox, gtexgwas, bedpe-domain and gcnv (without a type=gcnv track line) are not inferred from their extension, so they need an explicit format. Even then inferTrackType sends them to annotation, so the user must also set type.
An explicit type is trusted. config.type skips inference entirely, so a mismatched pair (say, type: "wig" on a VCF) builds the wrong class with no check at load time that the class can draw that data.
