How igvjs-mcp works

Five parts, three on the internet and two on the person’s computer, cooperate so that a model can drive the igv.js genome browser from a conversation. A person knows the result as igv-bot. This document shows what each part is, which wires join them, and what crosses each wire.

The parts and the wires

The Host’s request to the Worker comes from Anthropic’s or OpenAI’s servers, not from the person’s computer. That is why the Worker needs a public https:// address even during local development, and why a local Worker is tried in those Hosts through a tunnel.

Two things carry the whole design. First, the Worker draws nothing and loads no genomic data: igv.js runs only in the Viewer, a web page in the person’s Side panel, and fetches its genomes and tracks from the data hosts itself. Second, the Worker cannot reach the Viewer by itself. It waits for the Viewer to open a WebSocket to the Room named in its Join link, and pushes every Command down that socket.

So a single request from the model crosses two wires on the way out (A, then B) and the same two on the way back. Everything else in the figure exists to set those wires up, to feed igv.js its data, and to keep the Room’s copy of the view in step with the Viewer.

Three wires are missing on purpose. The Worker never serves the Viewer: anything but /mcp and /ws is answered 404, and the page comes from its own site. The Join card never holds the genome browser: the Host’s sandbox forbids framing another site, so the card carries a link and a button and nothing more. And the Viewer never calls /mcp: it reaches the Worker only through its Room’s socket.

One Room id, three ways in

A Room ties one conversation to its Viewer. It is a Cloudflare Durable Object, one per Room id, and the id is ten Crockford base32 characters, short enough to sit in a Join link and long enough to be unguessable. A tool call can name its Room in three ways, and the Worker takes the first it finds.

The two headers predate the room argument and are kept as fallbacks. ChatGPT does not echo mcp-session-id but sends x-openai-session on every request; the Worker turns that into a Room id with HMAC-SHA256 under the SESSION_HMAC_SECRET secret, so the raw value never appears in a link.

The Room id comes from the model on every call rather than from the MCP session because a Host does not keep one session per conversation. Claude desktop makes its first calls from the chat and, once the model has used the Side panel, every later call from a second MCP session with a Room of its own, which is empty. The model is the one thing that stays with the conversation (ADR 0003).

For the same reason open_viewer without room never returns the MCP session’s Room: it mints a new one. The chat’s MCP session is shared by several conversations, and a Room shared between them would open one conversation’s igv-bot on another’s last view. A new conversation starts on the default view; open_viewer with room gets the same igv-bot back.

Scenario: “open igv-bot”

The person types “open igv-bot”. The model calls open_viewer, and a few steps later the Viewer shows hg38 and its status line reads “Connected”. Only the second step involves the model.

WireWhat happens
1AThe Host posts initialize. The Worker answers with a freshly minted Room id as the mcp-session-id header, which the Host sends back on later requests. That Room is only a fallback; no Join link ever names it.
2AThe model calls open_viewer. The Worker mints a new Room id and replies with it and the Join link, https://igv-bot-web-dev.pages.dev/?room=7KQ2M9XA4T. The Viewer is not contacted, and nothing is stored in the Room. The reply tells the model to open the link in the Side panel if it has one, to pass the Room id on every later call, and to repeat neither to the person.
3A, FA Host that renders MCP Apps reads the Join card from the Worker and hands it the result. The card shows one line of status and an Open igv-bot button. Other Hosts show the text link.
4The model opens the Join link in Claude desktop’s Side panel. Where it cannot, the person presses Open igv-bot, and the card asks the Host to open the link; ChatGPT desktop in Codex mode reaches its Side panel this way. Where a Host has no Side panel, the link opens in a browser tab, and everything after works unchanged.
5CThe Side panel fetches the Viewer page from its static site.
6BThe Viewer reads the Room id from its own address and opens a WebSocket to /ws?room=. The Worker refuses any Origin not on VIEWER_ORIGINS and hands the socket to the Room, which answers join with joined, carrying the Session saved there if there is one.
7DOnly now does igv.js start: on the saved Session, or on the default view, hg38 in whole-genome view with its gene annotation track. It fetches the genome from the data hosts itself.
8BThe Viewer sends its first report: the Session, as igv.js writes it, and the Session summary. The Room keeps both. The status line reads “Connected · Room 7KQ2M9XA4T”.
open_viewer also takes genome and locus, for a new Room only. The Worker checks the genome on the igv.org list (wire E) before minting anything, then saves the two in the new Room as its Session. The Viewer restores them in step 7 like any saved Session.

igv.js waits for step 6 on purpose. Started any earlier, it would draw the default view and then throw it away for the saved one. A Command that arrives while igv.js is still loading waits for it.

Scenario: “go to MYC”

With igv-bot open, the person asks to go to MYC. The model calls go_to_gene. The call travels out along A and B, and its answer returns along the same wires, carrying the Session summary with it.

WireWhat happens
1AThe Host posts tools/call for go_to_gene with gene and room. The Worker reads the Room id, in any case and with spaces trimmed, and refuses one that is malformed.
2The Worker asks the Room to send the Command {type: go_to_gene, gene: MYC}. Every Command tool does exactly this; each is one row of server/src/commandTools.ts.
3BThe Room gives the Command a request id, pushes it to every Viewer in the Room, and waits up to 15 s for the first ack.
4DThe Viewer applies the Command to igv.js, one at a time and in the order they arrive. igv.js looks MYC up and fetches what the new view needs directly from the data hosts, not through the Worker.
5BThe Viewer acks with the request id, ok or igv.js’s own error, and the Session summary as it now stands. The Room keeps the summary.
6The Room hands the outcome back to the Worker. A later ack of the same Command, from a second Viewer, finds nothing waiting and is dropped.
7AThe Worker replies “Done.” with the Session summary: genome, loci, the tracks in display order with their heights, and whether the crosshairs and centre line are showing. The model turns it into its answer.
8Bigv.js announced the move, so once it has been quiet for a quarter of a second the Viewer sends the Session and its summary. The Room keeps both, for a Viewer that opens later.
An unknown gene is not a failed call. igv.js reports that it found nothing, the Viewer acks with that error and the unchanged summary, and the model is told so in igv.js’s own words.

The reply always carries a Session summary because the model cannot see the screen. Each answer tells it what is there now, so its next call can name a track by its position or its name without asking first.

When the person changes the view

The person also works in igv.js directly: panning, zooming, dragging tracks into a new order, removing one, using a track’s gear menu. None of this goes through the model, and the model is not notified.

The Viewer listens for igv.js’s change events, whoever caused them. When igv.js has been quiet for a quarter of a second it sends the Room the Session and its summary along B, so a drag that fires an event on every frame is one message. A Session the Room already has is not sent again, and one reported while the socket is down is sent on the next join. igv.js announces nothing when its crosshairs or centre line button is pressed, so the Viewer also treats a click in the browser as a possible change.

The model learns of a hand change in one of two ways: from the Session summary in the reply to its next call, or by asking with read_session_summary, a Command that changes nothing. Its description tells the model to ask before acting on “this region” or “the second track”.

Calls that stop at the server

Of the 14 tools, 12 are Commands and follow Figure 4. Two never reach the Viewer at all, and one Command is checked against the genome list before it is sent.

ToolWiresWhat the Worker does
open_viewerA, and E when given a genomeMints a Room id, or renews the one it is given, and builds the Join link. With genome or locus, saves them in the new Room for the Viewer to restore. Sends the Viewer nothing.
search_cataloguesA, EReads the genome from the Room’s last Session summary unless given one, fetches that genome’s ENCODE and 4DN tables, and replies with the count of all matching rows and at most 20 of them, each with the name and URL to load it. Sends the Viewer nothing.
change_genomeA, E, then BLooks the genome up on the igv.org list first. One that is not there is refused with the list of those that are, and the Viewer is left as it was. One that is there is sent, spelled as the list spells it.
igv.org refuses requests that do not come from a browser, a Worker’s among them, so the deployed Worker ends up reading igv.js’s own backup of the genome list, on GitHub. The Catalogue tables come from the same repository; ENCODE’s for one genome hold some 190,000 rows.

A search finds tracks; it does not load them. The model passes the rows it picked to load_tracks, a Command, and igv.js fetches each file from its URL along D.

What each part keeps

The table says what survives between requests, and where. The Viewer is the source of truth for what is on screen; the Room’s copy is a mirror, read only by a Viewer that opens later and by a search that needs the genome.

PartKeepsFor how long
The modelThe Room id, in the conversationAs long as the conversation
The HostThe mcp-session-id from initializeAs long as the MCP session
Worker, at /mcpNothing per request: each gets a fresh MCP server. Per Worker instance, the genome list and one genome’s Catalogue tables.An hour each, then fetched again
RoomThe Viewer’s socket, Commands waiting for an ack, the latest Session summary, and the last SessionDeleted 24 hours after the last message from a Viewer, unless a Viewer is still connected; the Room is then marked expired
Join cardThe Join linkAs long as the conversation shows it
ViewerThe Session: genome, loci, tracks, heights, crosshairs, centre lineUntil the page closes; restored from the Room when the Join link is opened again

Only a Viewer that has just been opened restores the Room’s Session. One that loses its socket and rejoins keeps its own, since its own is the truth. Reopening the Join link therefore brings back the last view, and nothing has to enforce one live Viewer per Room.

When something goes wrong

What happensWhereWhat the model or the person sees
A call’s room is not a Room idAThe Worker refuses it, and says to pass the Room id from open_viewer’s reply.
A call carries no room, and its MCP session’s Room has no ViewerAAn error that says to call again with room, or to open igv-bot first.
Only x-openai-session arrives, and the secret is not setAThe request fails as a server misconfiguration. There is no fallback key.
A genome is not on the igv.org list, or the list cannot be readEAn error listing the genomes available, or saying to try again. Nothing is sent to the Viewer.
The Catalogue tables cannot be readEAn error that says to try again.
No Viewer has joined the RoomBAn error that says to call open_viewer with this room and open its Join link.
The Viewer does not ack within 15 sB“Sent, unconfirmed”, with the Session summary the Room last heard, from before the call.
igv.js raises an error applying a CommandB, Digv.js’s own message, with the Session summary. For load_tracks, the other tracks of the call are still loaded.
The Viewer’s socket dropsB“Connection lost. Reconnecting…”. The Viewer rejoins after 1 s, 2 s, up to 5 s, and sends any report it is owed. igv.js still works by hand meanwhile.
The Viewer joins an expired RoomB“This igv-bot has expired.” The Room closes the socket and the Viewer does not retry. open_viewer with that room renews it, and the Join link works again.
The Viewer is served from an origin not on VIEWER_ORIGINSBThe socket is refused with 403. The Viewer stays at “Reconnecting…”.
The saved Session does not loadDThe Viewer shows the default view instead, so a reload does not fail the same way again.

Addresses

These are the development deployment. Both parts run on one Cloudflare account, the one that owns the 3dg.io zone. They are deployed as a matched pair: the Worker names the Viewer’s address in VIEWER_URL, and the Viewer is built with the Worker’s address in VITE_SERVER_URL, fixed at build time.

Workerhttps://igv-bot-mcp-dev.3dg.io/mcp for Hosts, /ws for Viewers

Locally the Worker runs on localhost:8787 and the Viewer on localhost:5173, and the Viewer reaches its Room through its own address: the Vite dev server passes /ws on to the Worker. Claude desktop’s Side panel blocks a page from opening a socket to another local address.

The words used here (Host, Connector, Side panel, Viewer, Room, Command, Session, Session summary, Join link, Join card, Catalogue, Shareable URL) are defined in GLOSSARY.md. The decision to show the Viewer as a web page in the Side panel is ADR 0001, the decision to push Commands through a Room is ADR 0002, and the decision to have the model carry the Room id is ADR 0003.
